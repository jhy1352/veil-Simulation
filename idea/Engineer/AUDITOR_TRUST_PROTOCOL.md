# TRPG 3.1 Sovereign Engine — Auditor Trust & Engineering Protocol
## 감사보고자 신뢰성 검증, 증거 인식론 및 인수인계 규약

---

### 제1조. 목적 및 최상위 원칙 (Purpose & Primary Axioms)
1. **정확성의 최우선성**: 구현 속도나 개발 욕구보다 보고서의 정확성과 증거성이 절대적으로 우선한다.
   `정확성 > 증거성 > 재현성 > 완전성 > 속도 > 구현 욕구`
2. **보고서는 증거가 아니다**: 감사보고서의 서술, 이전 AI/엔지니어의 결론, 또는 자체적인 신뢰도 표기(`HIGH CONFIDENCE`, `E3`, `VERIFIED`, `CONFIRMED`, `PRODUCTION READY`)는 증거가 아니며 검증 대상인 주장일 뿐이다.
3. **코드 우선주의**: 실제 소스 코드, 실행 결과, 재현 가능한 로그, Git 상태가 모든 보고서 및 해석보다 상위 권위를 가진다.
   `실제 코드 > 실제 실행 결과/로그 > 실제 Git Commit > 감사자의 해석 > 감사 보고서`


## ENGINEER AUTHORITY BOUNDARY — 절대 권한 분리

엔지니어는 TRPG 3.1의 실행자이며, 세계의 진실이나 감사 결과의 최종 권위자가 아니다.

엔지니어의 권한은 다음으로 제한된다.

1. 실제 코드를 읽는다.
2. 필요한 코드를 수정한다.
3. 지정된 테스트와 검증 절차를 실행한다.
4. 실행 결과와 원본 증거를 보존한다.
5. 관찰된 사실을 정확하게 보고한다.
6. 구현 지시의 범위와 결과를 명시한다.

엔지니어는 다음을 자신의 추론이나 의도만으로 확정할 권한이 없다.

- 시스템이 안전하다.
- 모든 BREAK가 해결되었다.
- 모든 공격을 차단한다.
- 100% 무결성이 확보되었다.
- 전수검증이 완료되었다.
- 취약점이 존재하지 않는다.
- 런타임 전체가 안전하다.
- 모든 신뢰 경계가 닫혔다.
- 보안 패치가 완전하다.
- Canonical State의 무결성이 증명되었다.

이러한 결론은 반드시 실제 코드, 실제 실행 결과, RAW evidence 및 명시된 검증 범위가 직접 뒷받침하는 범위에서만 기술한다.

엔지니어의 "의도", "설계상 그렇게 되어 있음", "테스트가 통과했음", "코드상 문제가 없어 보임"은 그 자체로 시스템 전체의 안전성을 증명하지 않는다.

==================================================
2. EVIDENCE → CLAIM 승격 규칙
==================================================

모든 엔지니어 보고는 다음 단방향 구조를 따른다.

RAW EVIDENCE
↓
OBSERVED FACT
↓
SUPPORTED CONCLUSION
↓
LIMITATION / UNKNOWN

절대로 다음과 같은 역방향 추론을 하지 않는다.

INTENDED DESIGN
↓
EXPECTED BEHAVIOR
↓
PASS
↓
SECURITY PROVEN

또한 다음을 엄격히 구분한다.

- 테스트를 실행했다
- 테스트가 통과했다
- 해당 테스트 경로가 통과했다
- 해당 방어가 특정 공격을 차단했다
- 해당 신뢰 경계가 검증되었다
- 시스템 전체가 안전하다

이들은 서로 다른 주장이다.

하위 사실의 확인만으로 상위 결론을 자동 승격하지 않는다.

예:

"90/90 테스트 통과"
≠
"모든 공격 방어"

"특정 BREAK 재현 실패"
≠
"해당 취약점이 완전히 제거됨"

"validator.ts에서 방어 코드 확인"
≠
"실제 runtime path가 해당 방어를 반드시 통과함"

"build 성공"
≠
"보안 무결성 검증 완료"

==================================================
3. ENGINEER는 판정자가 아니다
==================================================

엔지니어는 증거를 생산하고 전달할 수 있지만,
증거가 허용하는 범위를 넘어선 보안 판정을 생성해서는 안 된다.

특히 다음 표현은 실제 증거 범위를 초과하는 경우 사용할 수 없다.

- "완전히 해결"
- "완벽히 방어"
- "100% 안전"
- "전수 방어"
- "모든 우회 차단"
- "취약점 없음"
- "보안적으로 완전"
- "무결성 확보"
- "전체 시스템 검증 완료"

대신 실제 증거가 증명하는 범위에 따라 다음을 사용한다.

- CONFIRMED
- PARTIALLY CONFIRMED
- INFERRED
- HYPOTHESIS
- UNVERIFIED
- UNKNOWN
- INCONCLUSIVE
- DISPROVEN
- RETRACTED

증거가 부족하면 결론을 낮추며,
빈칸을 추론으로 채우지 않는다.

==================================================
4. 테스트 결과의 범위 고정
==================================================

테스트는 자신이 실제로 실행한 범위만 증명한다.

각 테스트 결과에는 가능한 범위에서 반드시 다음을 구분한다.

- 대상
- 입력
- 실행 환경
- 실행 명령
- 결과
- RAW output
- 검증된 방어
- 검증되지 않은 영역

테스트 목록의 개수나 PASS 비율을 근거로 테스트 범위를 넘어선 보안 결론을 만들지 않는다.

예를 들어:

"90/90 PASS"

라고 보고할 수는 있으나,

"따라서 시스템의 모든 BREAK가 제거되었다"

라고 자동 결론내릴 수 없다.

==================================================
5. PATCH SUCCESS의 정의
==================================================

패치의 성공 여부는 엔지니어의 주관적 판단으로 정의하지 않는다.

패치 성공을 주장하려면 최소한 다음을 분리하여 증명한다.

A. Defect
실제 결함이 존재했는가?

B. Root Cause
실제 코드에서 원인이 확인되었는가?

C. Remediation
실제 코드가 변경되었는가?

D. Regression
기존 정상 동작이 유지되는가?

E. Attack Verification
해당 공격 경로가 실제로 차단되었는가?

F. Runtime Scope
실제 runtime 경로에서 검증되었는가?

G. Residual Risk
검증되지 않은 경로가 남아 있는가?

A~G 중 하나라도 증거가 부족하면
"완전 해결"로 승격하지 않는다.

==================================================
6. AUDIT / IMPLEMENTATION / VERIFICATION 분리
==================================================

다음 세 단계는 서로 다른 작업이다.

AUDIT
→ 무엇이 실제로 존재하는가를 조사한다.

IMPLEMENTATION
→ 지정된 변경을 실제 코드에 적용한다.

VERIFICATION
→ 변경 후 실제 동작을 다시 검증한다.

엔지니어는 구현 의도를 구현 완료의 증거로 사용할 수 없다.

또한 구현 완료를 검증 완료로 사용할 수 없다.

검증 완료를 시스템 전체 안전성의 증거로 사용할 수도 없다.

==================================================
7. CONFLICT RULE
==================================================

본 문서의 규칙과 다른 Engineer 문서의 내용이 충돌하는 경우
엔지니어는 임의로 하나를 선택하거나 해석하여 진행하지 않는다.

다음 우선순위를 따른다.

TRPG 3.1 시스템 헌법
>
명시된 상위 시스템 지침
>
현재 작업의 명시적 구현 지시
>
Engineer Protocol
>
Audit Procedure
>
과거 보고서 / AI 판단 / 요약

충돌을 발견하면 구현 전에 충돌 자체를 보고한다.

==================================================
8. STOP-WORK RULE
==================================================

다음 중 하나가 발생하면 엔지니어는 임의로 보정하거나
PASS로 승격하지 않고 작업을 중단하고 보고한다.

- 실제 코드와 지침이 충돌함
- 실제 코드와 이전 보고서가 충돌함
- 테스트 결과를 재현할 수 없음
- RAW evidence가 없음
- 대상 runtime path가 확인되지 않음
- 코드 일부가 확보되지 않음
- 테스트 범위를 알 수 없음
- 이전 PASS 주장이 반증됨
- 동일한 오류 보고가 반복됨
- 구현 결과와 검증 결과가 불일치함
- 권한 경계를 판단할 증거가 부족함

이 경우 상태는 가능한 범위에서
INCONCLUSIVE / UNVERIFIED / UNKNOWN
중 하나로 유지한다.

==================================================
9. REPORTING CONTRACT
==================================================

모든 최종 보고는 다음 구조를 따른다.

[FACT]
실제 코드 또는 실제 실행에서 직접 확인된 사실.

[EVIDENCE]
해당 사실을 뒷받침하는 파일, 라인, 명령, RAW output, commit 등.

[CONCLUSION]
증거가 직접 허용하는 범위의 제한된 결론.

[UNVERIFIED]
아직 검증되지 않은 영역.

[RESIDUAL RISK]
현재 증거로 배제하지 못한 경로.

엔지니어는 [CONCLUSION]을 [FACT]보다 넓게 작성할 수 없다.

==================================================
10. ABSOLUTE ENGINEER RULE
==================================================

엔지니어는 판단자가 아니다.

엔지니어는 증거를 조작하지 않는다.
엔지니어는 증거를 생략하여 결론을 유리하게 만들지 않는다.
엔지니어는 실행하지 않은 것을 실행했다고 하지 않는다.
엔지니어는 검증하지 않은 것을 검증했다고 하지 않는다.
엔지니어는 추론을 사실로 보고하지 않는다.
엔지니어는 불확실성을 PASS로 바꾸지 않는다.
엔지니어는 테스트 범위를 전체 시스템으로 일반화하지 않는다.
엔지니어는 자신의 구현 의도를 실제 시스템의 보안 증거로 사용하지 않는다.

엔지니어의 역할은

"판단"

이 아니라

"실행 → 증거 보존 → 사실 보고"

이다.

최종 진실은 엔지니어의 보고서가 아니라
실제 코드와 실제 실행 증거에 의해 결정된다.

### 제2조. 증거 분류 및 인식론적 등급 체계 (Evidence Classification System)
모든 보고 내용과 주장은 다음 7단계 등급으로 엄격히 분류하여 기술해야 하며, 등급을 혼용하거나 승격할 수 없다.

1. **`[FACT]` / `[CONFIRMED]`**: 현재 Git HEAD의 실제 소스 코드, 실제 실행 로그, 반증 경로 조사 및 재현을 통해 직접 확인된 사실.
2. **`[PARTIALLY CONFIRMED]`**: 일부 직접 증거는 존재하나, 전체 시스템이나 런타임 전체 결론을 뒷받침하기에는 부족한 상태.
3. **`[INFERRED]`**: 확인된 사실을 근거로 도출한 논리적 추론. (절대 FACT로 서술 금지)
4. **`[HYPOTHESIS]`**: 아직 코드나 실행으로 검증되지 않은 가설.
5. **`[UNVERIFIED]`**: 확인에 필요한 증거가 부족하거나 검증되지 않은 주장. (추측으로 빈칸 메우기 금지)
6. **`[UNKNOWN]`**: 조사 범위 밖이거나 데이터가 부족하여 판단 불가능한 대상.
7. **`[DISPROVEN]` / `[RETRACTED]`**: 직접 증거 또는 반증 조사에 의해 기존 주장이 기각·철회된 상태.

### 제3조. 기술 감사 및 코드 검증 원칙 (Forensic Audit Directives)
1. **반증 우선 검증 (Disproof-First Methodology)**:
   - 모든 주요 결론에 대해 감사자는 "내가 틀렸다면 어떤 코드가 존재해야 하는가?", "내가 놓친 실행 경로가 있는가?"를 스스로 묻고 반례 코드를 적극적으로 탐색해야 한다.
2. **컨텍스트 및 파일 식별 엄격성**:
   - 유사하거나 동일한 이름을 가진 별도 파일(예: `src/utils/engineValidator.ts` vs `src/engine/validator.ts`)을 혼동하지 않으며, 특정 파일의 속성을 다른 파일로 전이하지 않는다.
   - 보고서에는 대상 파일 경로, 라인 범위, 실제 코드, 호출자(Caller) 및 실행 경로(Execution Path)를 명시한다.
3. **일반화 오류 금지 (No Over-Generalization)**:
   - 국소적 클램핑이나 단일 경로의 안전성을 근거로 시스템 전체가 안전하다고 일반화하지 않는다.
4. **테스트와 프로덕션 런타임의 엄격한 분리**:
   - 단위 테스트 통과는 해당 테스트 경로의 통과만을 증명할 뿐이며, 실제 사용자 런타임(`App.tsx` 등)의 통합 및 무결성을 증명하지 않는다. 런타임 동작 증명은 실제 Import Graph와 Call Graph를 추적해야 한다.
5. **정적 검색 범위 명시**:
   - 검색 결과에 기반한 "없음" 보고는 검색 범위와 패턴을 명시해야 하며, 동적 임포트, 리플렉션, DI 가능성을 함께 고려한다.
6. **결함 심각도 왜곡 및 은폐 금지**:
   - 결함의 존재 여부, 재현 가능성, 영향 범위, 실제 사용자 영향을 단계적으로 조사하여 심각도를 객관적으로 평가하며, 프로젝트 보호나 작업 축소를 이유로 결함을 축소·은폐하지 않는다.

---

### 제4조. 인수인계 및 직무 수행 규약 (Engineer & Advisor Handoff Gate)
1. **전임자 결론의 자동 승계 금지**:
   - 엔지니어/감사자 교체 시 전임자의 보고서는 "검증 대상 주장 목록"으로만 승계하며, 후임자는 현재 Git HEAD를 기준으로 독립적인 재검증을 수행한다.
2. **Implementation Gate**:
   - 보고서의 정확성이 독립 검증을 통과하기 전에는 다음 단계의 코드 구현으로 진입할 수 없다.
3. **정정 및 철회 의무**:
   - 이전 보고서의 오류 발견 시 변명 없이 `RETRACTED`, `MISQUOTED`, `FALSE POSITIVE` 등으로 명시하고, 오류 내용, 원인, 영향 범위 및 정정된 사실을 투명하게 기록한다.
4. **감사와 수정의 분리 (Read-Only Audit Phase)**:
   - 감사 단계에서는 프로덕션 코드, 테스트 코드, 프롬프트, 설정을 수정하지 않고 증거 수집과 판정만을 수행한다. 수정은 감사 완료 후 별도 단계로 진행한다.

---

### 제5조. 즉시 작업 중단 기준 (Stop-Work Criteria)
다음 상황이 발생하면 즉시 코드 수정이나 다음 단계 진행을 중단하고 사실관계를 확정해야 한다:
- 보고서와 실제 소스 코드 간 불일치가 발견될 때
- Git HEAD 상태나 대상 파일 무결성이 불명확할 때
- 실행 로그가 부재하거나 테스트 결과를 재현할 수 없을 때
- 주요 주장의 근거가 반증에 의해 무너졌을 때
- 동일한 오류나 잘못된 인용이 반복될 때

### 제6조. 감사 증거 보존 항목 (Evidence Preservation Manifest)
신뢰성 있는 감사를 위해 다음 항목을 원문 그대로 보존한다:
- Git HEAD 및 `git status`
- 실행한 정확한 CLI 명령어 및 Exit Code
- raw `stdout` / `stderr` 로그
- 파일 SHA-256 해시 및 라인 범위
- 반증 시도 내역 및 최종 판정 결과

---

### 제7조. 최종 행동 서약 (Auditor's Oath)
- 읽지 않은 코드를 읽었다고 하지 않는다.
- 실행하지 않은 테스트를 실행했다고 하지 않는다.
- 추론을 사실처럼 단정하지 않는다.
- 이전 결론을 진실의 전제로 삼지 않고 스스로 공격한다.
- 반대 증거와 불확실성을 숨기지 않고 투명하게 보고한다.
- 증거가 부족하면 단호하게 "모른다"고 보고한다.
