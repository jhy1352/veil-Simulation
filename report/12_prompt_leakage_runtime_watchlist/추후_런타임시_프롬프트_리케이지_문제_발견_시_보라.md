# 추후 런타임시 프롬프트 리케이지 문제 발견 시 보라

## 목적
P0-3에서 확인된 프롬프트 리케이지 관련 상태를 기록하고, 향후 실제 런타임 테스트에서 동일하거나 유사한 현상이 재발하면 이 문서를 기준으로 원인을 재포렌식한다.

## 현재 판정

- **FACT / GREEN:** `3eee9f3`에서 기존 프롬프트의 설명용·예시성 leakage 일부가 제거되었다.
- **FACT / YELLOW:** 현재 유효한 시스템 지시에는 `PICKUP`, `GIFT`, `SUBJECT`, `TARGET`, `OBJECT` 등 구체적인 schema vocabulary가 남아 있다. 이것이 단순 normative schema인지 실제 leakage인지는 별도 판정이 필요하다.
- **UNKNOWN / RED:** 현재까지 확보된 단일 런타임 증거만으로 프롬프트 리케이지가 완전히 종결되었다고 입증할 수 없다.
- **UNKNOWN / RED:** 과거 Triage stamp가 모델 입력 컨텍스트에 실제로 주입된 것인지, 모델이 이전 컨텍스트를 재생산한 것인지, 다른 경로에서 삽입된 것인지 원인은 확정되지 않았다.
- **UNKNOWN / RED:** 장기 대화/500-turn 규모에서 이전 내부 지시, Triage stamp, 이전 Candidate 데이터 등이 재주입 또는 재생산되지 않는다는 것은 아직 입증되지 않았다.

## 런타임 재발견 시 반드시 확인할 순서

1. **실제 Phase 1 모델 입력 전체를 원본으로 보존한다.**
2. 모델 raw response를 responseId 및 timestamp와 함께 보존한다.
3. Triage 입력과 출력이 동일한 원본인지 비교한다.
4. Recovery 입력/출력에서 내부 지시나 stamp가 새로 삽입되는지 확인한다.
5. Candidate payload 내부에 이전 Triage stamp, 내부 instruction, 이전 Candidate 데이터가 들어오는지 확인한다.
6. Phase 2 입력에도 Phase 1의 내부 정보가 의도치 않게 전달되는지 확인한다.
7. 동일 문자열의 최초 발생 위치를 EOF까지 역추적한다.
8. 모델 입력에 존재했다면 **LLM context contamination 가능성**, 모델 입력에 없었다면 **runtime insertion path**를 우선 조사한다.

## 특히 확인할 증거

### A. Triage stamp

Triage stamp가 발견되었다는 사실만으로 Triage가 현재 실행에서 새로 생성했다고 판단하지 않는다.

반드시:

`model input → model raw output → Triage input → Triage output`

순서로 최초 발생 지점을 확정한다.

### B. 내부 vocabulary

`PICKUP`, `GIFT`, `SUBJECT`, `TARGET`, `OBJECT` 등의 문자열이 존재한다는 사실만으로 leakage라고 판정하지 않는다.

확인할 것:

- 해당 문자열이 normative schema 계약에 필요한가?
- 설명용 예시로 사용되는가?
- 모델에게 특정 행동/서사 패턴을 유도하는 문맥에 포함되는가?
- 이전 대화나 이전 Candidate의 구체적 값과 함께 재주입되는가?

### C. 이전 런타임 정보

이전 Triage stamp, 이전 Candidate, 내부 diagnostic, engine state 등이 모델 입력에 포함되는 경우 단순 vocabulary 문제보다 우선순위가 높은 leakage로 취급한다.

## 재현 시 판정 규칙

- **GREEN:** 모델 입력에 내부 정보가 없고, 출력에도 재생산되지 않으며 반복 테스트에서 동일 현상이 재현되지 않음.
- **YELLOW:** normative schema vocabulary만 존재하거나 leakage 여부가 불명확함.
- **RED:** 내부 instruction, Triage stamp, 이전 Candidate/diagnostic 데이터 등이 모델 입력 또는 출력에 실제로 존재하고 그 경로가 의도되지 않은 경우.
- **UNKNOWN:** 최초 발생 위치 또는 입력 컨텍스트를 확보하지 못한 경우. 추측으로 GREEN 처리하지 않는다.

## 수정 원칙

1. 원본 evidence를 먼저 보존한다.
2. 최초 발생 지점을 확정한다.
3. 원인이 확인된 삽입/전달 경로만 최소 수정한다.
4. 프롬프트를 불필요하게 전면 재작성하지 않는다.
5. 수정 후 동일 입력과 장기 컨텍스트에서 재현 테스트한다.
6. 테스트 결과가 없으면 '완전 해결'로 선언하지 않는다.

## 현재 상태

**WATCHLIST / 후속 런타임 검증 필요.**

현재 P0-3에서 일부 명시적 예시 leakage가 제거된 것은 확인되었지만, **프롬프트 리케이지 전체가 완전히 종결되었다는 것은 입증되지 않았다.**
