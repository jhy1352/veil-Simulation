# Pipeline Integration / Optimization — Forensic Baseline

## Scope
Current branch: `work/pipeline-prune-from-ea8ca300`

Target production flow:

LLM #1 → Triage → Candidate Recovery → Semantic Translation → Diversity → PreAuth → LLM #2 → Sovereign Commit

This document records concrete integration/optimization targets found from current code. It does not declare unrelated issues fixed.

## FACT 1 — Candidate Recovery is already the single parser/recovery authority

`candidateRecoveryGate.ts` receives the raw candidate block, calls `parseCandidatesBlock()`, and `parseCandidatesBlock()` calls `recoverSyntaxAndParseJson()`.

Therefore production must not add another JSON/recovery pass before or after this gate without evidence that the existing gate is insufficient.

## FACT 2 — Production server contains redundant legacy imports

`server.ts` imports:
- `extractCandidatesFromMetadata`
- `buildSafeProposalFromCandidate`
- `recoverSyntaxAndParseJson`

The current `/api/chat` pipeline does not call these functions in the observed server flow. They should be removed only after repository-wide call-site verification confirms they are not required for another exported/runtime path.

## FACT 3 — The server has a contradictory semantic fallback

Current server translation does:

```text
getCandidateSemanticEvents(candidate)
→ if empty, getCandidateSemanticEvents(candidate.rawMetadata)
→ compileCandidateToProposal()
```

But `candidateRecoveryGate.ts` defines `rawMetadata` as an allow-listed external object whose permitted keys do not include `semanticEvents`. `semanticCandidateContract.ts` separately defines `semanticEvents` as a top-level candidate field.

Therefore the `rawMetadata` semanticEvents fallback is structurally inconsistent with the current external contract and is a strong candidate for removal.

Do not silently replace it with semantic invention or legacy rawMetadata proposal construction. A candidate with no valid semanticEvents should remain `TRANSLATION_MISSING` unless a separately audited migration path is intentionally retained.

## FACT 4 — Candidate compilation currently performs runtime mapping twice

`runtimeSemanticCandidate.ts` currently:

1. calls `semanticEventsToRuntimeActions()` to construct Proposal.actions;
2. then calls `enrichMeaningTreeWithRuntimeActions()`;
3. that enrichment loops over the same SemanticEvents and calls `semanticEventToRuntimeActions()` again.

This duplicates deterministic identity/provenance/inventory resolution work and creates two opportunities for mapping behavior to diverge.

## FACT 5 — RuntimeProjection is another semantic→runtime projection boundary

`runtimeProjection.ts` can reconstruct/find SemanticEvents from MeaningTree ACTION nodes and call `semanticEventToRuntimeActions()`.

The current architecture therefore has:

```text
Candidate → SemanticEvents → Bridge → Proposal.actions
                       ↓
                  MeaningTree
                       ↓
              RuntimeProjection → actions
```

The second projection is currently used as a consistency/security check, which is valid as a check, but the implementation should be simplified so there is one authoritative deterministic projection result rather than two independently executed mappings.

Any consolidation must preserve the current security behavior, including fail-closed handling of unsupported/unresolved semantics and MeaningTree/action consistency.

## FACT 6 — Diversity filtering has an avoidable O(N²) re-match in server.ts

The server first calls `filterDiverseCandidates()` and then searches the retained list again with `.some(...)` for every successful translation.

The retained candidate identities can be indexed once with a `Set`, preserving exactly the same ordering and membership while removing unnecessary repeated scans.

This is a safe optimization candidate, not a semantic change.

## FACT 7 — Triage is currently not a semantic triage authority

`triageModule.ts` currently:
- checks/creates `TRIAGE_STAMP_V1`;
- extracts `[CANDIDATES_BLOCK]...`;
- returns the block to Candidate Recovery;
- prepends a stamp to the stored `rawResponseText`.

It does not perform causal analysis, semantic correction, identity rescue, or canonical decisions.

Therefore do not expand Triage during this integration task. Its current responsibility should either remain a minimal provenance/extraction boundary or be removed after call-site/evidence analysis. In particular, do not let Triage become a second semantic authority.

## FACT 8 — Phase 2 is still executed when no Candidate is authorized

Current server behavior builds a Phase 2 prompt with an explicit no-authorized-candidate branch and still calls LLM #2.

This is not automatically a bug: narrative output still needs to be generated. However, the runtime evidence already showed that Phase 2 can produce structured semantic-looking text even when `selectedCandidateId` is null.

Therefore optimization must not accidentally allow Phase 2 output to re-enter Candidate/Proposal/Commit processing.

## Integration order

### P1 — One semantic transport source

Remove the contradictory `candidate.rawMetadata` semanticEvents fallback after call-site verification.

Required invariant:

```text
Candidate.semanticEvents
    ↓
semantic contract validation
    ↓
CausalCompiler
```

No semantic meaning is recovered from rawMetadata or narrative prose at this boundary.

### P2 — One deterministic runtime projection

Refactor Candidate compilation / RuntimeProjection so the runtime action sequence is derived from one deterministic projection result.

The consistency gate may recompute independently for security if required, but the production compiler should not perform redundant bridge mappings merely to enrich the same tree.

Before changing behavior, add/adjust tests for:
- valid executable event;
- QUERY / HEARSAY / NEGATED / INTENTIONAL non-mutation;
- compound executable + non-executable events;
- unsupported-only event;
- unresolved identity;
- invalid provenance;
- zero-action proposal;
- MeaningTree/action mismatch.

### P3 — Production dead-path cleanup

After repository-wide call-site verification:
- remove unused server imports;
- identify legacy proposal/parser paths that are no longer reachable from `/api/chat`;
- do not delete legacy modules until tests and exported entry points prove they are unused.

### P4 — Cheap deterministic performance cleanup

Replace the server's post-diversity O(N²) membership scan with a Set lookup.

Do not change candidate ordering or diversity semantics.

### P5 — Triage simplification

Only after P1–P4 and runtime regression tests:
- determine whether Triage is needed as a distinct runtime boundary;
- if retained, keep it structural/provenance-only;
- if removed, preserve raw model evidence and Candidate Recovery as the sole parsing/recovery authority.

No semantic authority is to be moved into Triage.

## Non-goals

Do NOT use this task to:
- redesign the world model;
- solve the unresolved semanticEvents watchlist without runtime reproduction;
- declare prompt leakage fully fixed;
- reintroduce the deterministic Korean natural-language parser into production;
- give LLM #2 canonical authority;
- replace engine validation with LLM judgment;
- perform unrelated refactors.

## Status

**FORENSIC BASELINE / IMPLEMENTATION TARGETS IDENTIFIED**

The current code already has substantial fail-closed authority barriers. The main integration problem is not absence of gates; it is duplicated/overlapping transformation paths and a few contradictory compatibility remnants. The next code changes should therefore consolidate existing authorities rather than add another layer.
