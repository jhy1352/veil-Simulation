# VEIL Pipeline Integration / Optimization — 현재 상태 및 다음 참모 인수인계

## 목적
현재 VEIL 엔진의 큰 작업을 `파이프라인 통합 및 최적화`로 전환한다. 이 문서는 다음 참모가 즉시 같은 기준으로 작업을 이어가기 위한 기준점이다.

## 최우선 원칙
- 코드/실제 runtime evidence > report > LLM/Studio 주장
- FACT / INFERENCE / HYPOTHESIS / UNKNOWN을 구분한다.
- GREEN/YELLOW/RED/UNKNOWN을 증거 수준에 맞게 사용한다.
- `verified`, `implemented`, `PASS` 등의 문구만으로 완료 판정하지 않는다.
- 기존 기능을 삭제하기 전에 실제 call-site/runtime reachability를 확인한다.
- 통합은 최소 변경으로 한다. 관련 없는 리팩터링 금지.
- 엔진의 canonical authority를 절대 LLM/Triage/Phase2로 이동시키지 않는다.

## 현재 확인된 실제 파이프라인
```text
Phase 1 Gemini
  ↓
runTriagePipeline(rawPhase1Response)
  ↓
rawCandidatesBlock
  ↓
runCandidateRecoveryGate()
  ↓
candidates
  ↓
compileCandidateToProposal()
  ↓
Diversity
  ↓
EngineValidator.validate()
  ↓
allowedCandidates
  ↓
Phase 2 Gemini
  ↓
selectedCandidateId
  ↓
selectedCandidate가 ALLOW 후보와 일치하는지 확인
  ↓
SovereignEngine.submitProposal()
  ↓
Canonical mutation
```

## 현재 코드상 핵심 사실
### Triage
`src/engine/language/triageModule.ts`는 현재 주로:
- TRIAGE_STAMP 감지/생성
- `[CANDIDATES_BLOCK]` 추출
- rawResponseText / rawCandidatesBlock 반환
- Candidate Recovery로 구조 복구 책임을 넘김

현재 Triage가 실제로 하지 않는 것으로 확인된 것:
- CausalCompiler 호출
- 인과 분석
- semantic event 판정
- history 기반 의미 구조 복원
- rejected Candidate 구조적 rescue
- canonical state 결정

따라서 Triage를 '의미 판단 계층'으로 전제하고 통합하지 말 것. 현재 구현은 훨씬 얇다.

### Recovery
Recovery는 JSON/문법/구조 손상 복구가 기본 책임이다.
- underlying information이 존재할 때만 구조를 복구
- 의미를 발명하지 않음
- action / role / epistemicStatus / polarity / cause / provenance / identity / semanticEvents를 임의 추론하지 않음
- malformed Candidate는 가능하면 해당 Candidate만 quarantine
- Candidate 간 독립성 유지

### Semantic Translation
Candidate의 semanticEvents를 읽어 CausalCompiler → MeaningTree → Runtime Bridge → StateTransitionProposal로 연결한다.

중요:
- semanticEvents가 없거나 invalid한 경우 의미를 Recovery에서 만들어서는 안 됨.
- `[]`로 조용히 collapse하는 지점이 존재할 가능성이 있어 watchlist 상태.
- 실제 historical Candidate loss는 아직 입증되지 않았다.

### PreAuth / Commit
Canonical mutation은 SovereignEngine의 commit 경계에서만 허용한다.
Phase1/Recovery/Semantic Translation/Diversity/PreAuth/Phase2 어디에서도 canonical truth를 독자적으로 확정하면 안 된다.

## 최신 P0-3 runtime 증거에서 확인된 것
실제 `/api/chat` HTTP 실행은 확인되었다.

Phase1 Candidate 예:
- action: QUERY
- target: 애꾸눈 무사
- object: 불사약의 전설
- epistemicStatus: UNVERIFIED

pipeline 결과:
```text
STAGE_0_EXTRACTION PASS
STAGE_1_RECOVERY_GATE PASS
STAGE_2_SEMANTIC_TRANSLATION REJECT
STAGE_3_DIVERSITY_GATE NOT_REACHED
STAGE_4_ENGINE_PREAUTH NOT_REACHED
STAGE_5_COMMIT_GATE NOT_REACHED
finalDisposition REJECT
```

Stage2에서 `UNVERIFIED` QUERY가 canonical translation 대상이 아니므로 거부되었다.
따라서 이 runtime에서는 canonical commit이 실행되지 않았다.

중요한 forensic correction:
- `parsedCandidates.semanticEvents=[]`라는 과거 report 해석은 CandidateLifecycleTrace에 존재하지 않는 필드를 읽은 forensic script 문제였다.
- 실제 Candidate semanticEvents가 사라졌다는 증거로 사용하면 안 된다.
- `engine.json`의 `[EMPTY_PROPOSAL_REJECTED]` 역시 실제 SovereignEngine rejection이 아니라 forensic fallback 문구였다.
- 실제 runtime에서 SovereignEngine.submitProposal()이 호출되었다고 주장해서도 안 된다.

## Phase2의 주의점
최신 runtime에서는 `selectedCandidateId: null`인데도 Phase2 Gemini가 QUERY/CLAIM/OBSERVED 형태의 구조화된 semantic-looking output을 생성했다.

이것은 즉시 canonical mutation을 증명하지는 않는다.
하지만 다음 의미에서 YELLOW:
- Phase2가 rejected/unselected Candidate를 재창조하는 것처럼 보이는 경로가 존재
- Phase2의 출력은 narrative-only여야 함
- Phase2가 Recovery 또는 canonical event generator처럼 행동해서는 안 됨
- selectedCandidate가 실제 ALLOW Candidate와 일치하지 않으면 commit 금지

## Prompt leakage watchlist
P0-3 prompt patch에서 explanatory/example leakage 일부는 제거되었지만, live system instruction에는 `PICKUP`, `GIFT`, `SUBJECT`, `TARGET`, `OBJECT` 등의 normative schema vocabulary가 남아 있다.

이것 자체를 leakage라고 단정하지 않는다.
- normative contract인지
- explanatory example인지
- behavioral inducement인지
구분해야 한다.

과거 runtime의 TRIAGE_STAMP 관련 현상은 'Gemini가 이전 curl/context를 echo했다'는 설명이 있으나, 정확한 Phase1 input 전체가 확보되지 않으면 원인 확정 불가.

## 통합/최적화 작업의 1차 목표
다음 참모는 바로 코드를 수정하지 말고 먼저 현재 브랜치의 실제 call graph를 고정한다.

### 조사 대상
1. `src/app/api/chat/server.ts` 또는 현재 chat runtime 진입점
2. `src/engine/language/triageModule.ts`
3. `src/engine/language/candidateRecoveryGate.ts`
4. `src/engine/language/semanticCandidateContract.ts`
5. `src/engine/language/runtimeSemanticCandidate.ts`
6. `src/engine/proposalParser.ts`
7. `src/engine` 내 Semantic Translation / Diversity / PreAuth / SovereignEngine 연결부
8. 현재 branch에서 남아 있는 legacy natural-language parser 및 adapter

### 반드시 찾아야 할 것
- 실제 호출 순서
- 중복 parsing
- 동일 Candidate의 중복 representation
- Candidate → rawMetadata → proposal 등 중복 변환
- dead/legacy path
- `|| []`, `?? []`, `.filter(Boolean)`, `return null/undefined`, `continue` 등 silent-loss 후보
- 동일 검증을 여러 계층에서 반복하는 부분
- Phase2가 실제로 필요한 입력과 불필요하게 전달되는 내부 정보
- Triage와 Recovery의 중복 책임
- legacy `buildSafeProposalFromCandidate()`의 실제 runtime reachability

## 최적화의 정의
'코드가 예뻐짐'이 아니라 다음을 최적화 대상으로 한다.

- 불필요한 LLM 호출 감소
- 중복 parse/transform 감소
- Candidate representation 수 감소
- canonical path 단일화
- 불필요한 history/state 재스캔 감소
- validation 중복 제거
- silent data loss 제거
- runtime traceability 향상
- Phase2 narrative-only 경계 강화

## 통합 목표 구조
가능한 경우 다음과 같이 직선화한다.
```text
LLM Phase1
 ↓
Structural Recovery
 ↓
Canonical Candidate Contract
 ↓
Semantic Translation
 ↓
Diversity / Policy checks
 ↓
PreAuth
 ↓
ALLOW Candidate
 ↓
Phase2 narrative generation
 ↓
ALLOW Candidate identity binding 확인
 ↓
Sovereign Commit
```

단, 이것은 목표 구조이지 현재 구현 사실이 아니다. 실제 call-site 증거 없이 구조를 가정하여 코드를 삭제하지 않는다.

## semanticEvents 처리 방침
현재는 WATCHLIST로 유지한다.
런타임에서 실제 문제가 재현되면 다음 순서로 조사:
```text
LLM raw semanticEvents
 → CandidatePacket.semanticEvents
 → getCandidateSemanticEvents()
 → CausalCompiler
 → MeaningTree
 → Proposal
 → PreAuth
 → Commit
```
각 단계에서 `PRESENT / ABSENT / INVALID / EMPTY / DROPPED`를 구분한다.

## 다음 참모에게 요구하는 작업 순서
### STEP 1 — 현재 branch forensic baseline
- 현재 HEAD 확인
- server runtime 진입점 확인
- 위 pipeline 각 단계의 실제 call-site를 따라간다.
- report 문구를 코드 사실로 간주하지 않는다.

### STEP 2 — 책임 중복표 작성
각 모듈별로:
```text
입력
출력
canonical authority 여부
semantic responsibility
structural responsibility
history access
LLM 호출 여부
중복 책임
legacy 여부
실제 runtime reachability
```
를 기록한다.

### STEP 3 — 삭제 후보 분류
- GREEN: 실제 dead path이며 대체 경로가 증명됨
- YELLOW: legacy/중복으로 보이나 runtime reachability 미확정
- RED: canonical path와 연결 가능성이 있어 보존
- UNKNOWN: 증거 부족

### STEP 4 — 최소 통합 패치
한 번에 큰 refactor를 하지 않는다.
가장 명확한 중복 하나를 제거하고 테스트/정적 검증한다.

### STEP 5 — runtime regression
최소:
- 정상 입력
- malformed JSON
- malformed Candidate 하나 + 정상 Candidate 하나
- semanticEvents absent
- semanticEvents invalid
- rejected candidate + valid candidate
- Phase2 selectedCandidate mismatch
- canonical commit success
- canonical commit denial

### STEP 6 — 장기/반복 검증
가능하면 500-turn static/runtime simulation으로:
- Candidate loss
- prompt leakage 재발
- Phase2 semantic drift
- state mutation mismatch
- history continuity
- performance/storage regression
을 본다.

## 절대 금지
- Triage가 인과/의미를 판결하도록 확대
- Recovery가 prose에서 missing semantics를 추론
- Phase2가 rejected Candidate를 복구
- LLM output을 canonical truth로 승격
- `[]`/null로 오류 원인을 숨김
- legacy code를 '아마 안 쓰일 것'이라는 이유만으로 삭제
- report PASS를 runtime proof로 간주
- semanticEvents watchlist를 근거 없이 이번 통합 작업에 섞어 해결했다고 선언

## 현재 판정
**FACT / GREEN:** 실제 canonical commit은 SovereignEngine commit gate에 의해 통제되는 구조가 존재한다.

**FACT / YELLOW:** Triage는 현재 구현상 얇은 stamp/extraction 계층이며 의미/인과 판단 모듈로 보기 어렵다.

**FACT / YELLOW:** Phase2가 selectedCandidate null 상태에서도 semantic-looking structured output을 생성한 runtime evidence가 있다.

**UNKNOWN / RED:** 전체 legacy parser/adapter의 runtime reachability가 완전히 제거되었는지 아직 증명하지 않았다.

**UNKNOWN / YELLOW:** semanticEvents가 실제 runtime에서 Candidate loss를 일으키는지 아직 증명하지 않았다.

**UNKNOWN / RED:** prompt leakage 현상이 모든 context/long-run에서 재발하지 않는다는 증거는 없다.
